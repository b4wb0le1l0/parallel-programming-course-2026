## 1. Вспомнить Java на одной маленькой программе

Прежде чем читать код, различай три вещи. **Класс** — описание объектов и их методов. **Объект** — конкретный экземпляр, созданный через `new`. **Поток** — выполнение инструкций: он вызывает методы и работает с объектами. Обычный объект не получает собственный поток при создании. Даже у `Thread` создание объекта и запуск выполнения — два отдельных действия.

Когда начинается наш `main`, один поток уже работает — главный, обычно с именем `main`. Он последовательно выполняет строки метода. Вызов обычного метода продолжает работу в этом же потоке: например, `accumulator.add(value)` не передаёт вычисление куда-то ещё.

Открой [S01Syntax.java](src/practice/S01Syntax.java). Здесь пока один поток.

Обрати внимание на синтаксис:

```java
long[] values = {3, 4, 9};
Accumulator accumulator = new Sum();
for (long value : values) {
    accumulator.add(value);
}
```

`long[]` — массив 64-битных целых. `new Sum()` создаёт объект; переменная `accumulator` хранит ссылку на него. `for (long value : values)` перебирает элементы. У массива длина — `values.length`, у списка размер — `history.size()`.

| Конструкция из файла | Как читать |
|---|---|
| `package practice;` | Класс относится к пакету `practice` |
| `import java.util.List;` | Разрешает писать `List` вместо полного имени |
| `public class S01Syntax` | Класс; имя публичного класса совпадает с именем файла |
| `private long total;` | Поле объекта, доступное внутри класса; изначально равно 0 |
| `void add(long value)` | Метод получает `long`, ничего не возвращает |
| `long total()` | Метод возвращает `long` |
| `interface Accumulator` | Контракт: какие методы должны быть у реализации |
| `implements Accumulator` | Класс реализует контракт |
| `@Override` | Компилятор проверит, что метод действительно реализует/переопределяет существующий |
| `static` у метода | Можно вызвать без создания объекта класса |
| `static final class Sum` | Вложенный класс без неявной ссылки на внешний объект; наследование запрещено |
| `final` у переменной | Её нельзя присвоить повторно; объект по ссылке может оставаться изменяемым |
| `List<Result>` | Список объектов типа `Result`; угловые скобки задают тип элементов |
| `new ArrayList<>()` | Конкретная реализация списка; тип элементов выводится из контекста |
| `record Result(...)` | Краткое описание объекта данных с конструктором и методами доступа |

`record Result(long count, long sum)` даёт методы `count()` и `sum()`, а не `getCount()`. Слово `record` в объявлении типа и метод `record(value)` из лабораторной — разные конструкции.

В `main` слово `static` позволяет JVM вызвать метод без `new S01Syntax()`. `String[] args` — аргументы запуска. Поля получают значения по умолчанию, но обычную локальную переменную перед чтением нужно инициализировать.

### 1.1. Интерфейс: что объект умеет делать

Класс описывает конкретные объекты: какие у них данные и как работают методы. Интерфейс позволяет сказать: «Мне подойдёт любой объект, у которого есть вот такие операции».

Представь, что программе нужно отправлять сообщения. Пока есть только отправка в консоль. Создай отдельный файл `InterfaceDemo.java` в пакете `practice`:

```java
package practice;

public class InterfaceDemo {
    interface Sender {
        void send(String text);
    }

    static class ConsoleSender implements Sender {
        @Override
        public void send(String text) {
            System.out.println(text);
        }
    }

    static void greet(Sender sender) {
        sender.send("Привет!");
    }

    public static void main(String[] args) {
        Sender sender = new ConsoleSender();
        greet(sender);
    }
}
```

Разберём связь между частями:

1. `interface Sender` объявляет операцию `send`: она принимает строку и ничего не возвращает. Здесь у метода нет тела — только обещание, что реализация его предоставит. Такой метод называется **абстрактным**.
2. `ConsoleSender implements Sender` означает, что класс выполняет это обещание. Поэтому он должен реализовать `send`. Метод интерфейса здесь неявно `public`, и реализация тоже должна быть `public`.
3. `new ConsoleSender()` создаёт конкретный объект. Сам интерфейс через `new Sender()` создать нельзя: способ отправки ещё не задан.
4. В `Sender sender = new ConsoleSender()` слева — тип переменной, справа — класс созданного объекта. Переменная хранит ссылку на этот объект; отдельный «объект интерфейса» не создаётся.
5. `greet` работает через интерфейс. При `sender.send(...)` выполняется метод конкретного объекта — здесь `ConsoleSender.send`.

Зачем это нужно? Добавь `LoudSender implements Sender`, который печатает `text.toUpperCase()`. Теперь можно вызвать `greet(new LoudSender())`, **не меняя код `greet`**. Выбор поведения через общий интерфейс называют полиморфизмом.

В первом упражнении ровно такая же связь: `Accumulator` задаёт операции, `Sum` хранит число и реализует эти операции. В лабораторной `MetricsCollector` задаёт `record()` и `snapshot()`, а разные классы реализуют их с разной синхронизацией. Замерялка сможет принимать `MetricsCollector` и вызывать одинаковые методы у всех вариантов.

Интерфейс сам не запускает поток и не добавляет защиту данных. Он задаёт доступные операции. Позже встретишь интерфейсы с готовыми `default`-методами; сейчас достаточно уметь читать такой простой контракт.

**Мини-упражнение:** добавь `LoudSender` и вызови `greet` сначала с обычным отправителем, потом с громким. Объясни, почему параметр `greet` в обоих случаях имеет один тип `Sender`.

### 1.2. record: короткий способ описать объект с данными

Допустим, метод должен вернуть два числа: сколько значений обработано и чему равна их сумма. Удобно объединить их в один объект:

```java
record Result(long count, long sum) {}
```

Java автоматически создаёт для него поля `private final`, конструктор и методы чтения. Вот основные части того, что иначе пришлось бы написать руками:

```java
final class Result {
    private final long count;
    private final long sum;

    public Result(long count, long sum) {
        this.count = count;
        this.sum = sum;
    }

    public long count() { return count; }
    public long sum() { return sum; }
}
```

Это поясняющий аналог, не полная замена: `record` дополнительно получает `equals`, `hashCode` и `toString`. Объявления выше — **два альтернативных варианта**, их не нужно вставлять вместе с одним именем.

Конструктор — код создания объекта, у него имя класса и нет возвращаемого типа. В `this.count = count` слева поле создаваемого объекта, справа аргумент конструктора. `this` означает «этот объект».

Использование `record` выглядит как работа с обычным объектом:

```java
Result result = new Result(3, 16);
System.out.println(result.count()); // 3
System.out.println(result.sum());   // 16
System.out.println(result);         // Result[count=3, sum=16]
System.out.println(result.equals(new Result(3, 16))); // true
```

Компоненты — значения, перечисленные в скобках объявления `record`, здесь `count` и `sum`. Изменить компоненты этого объекта нельзя: у него нет `setSum`, а поля `final`. Если нужны другие числа, создай новый `Result`. Дополнительные методы писать можно — например, `average()` в `S01Syntax`.

**Но неизменяемая ссылка не делает содержимое объекта неизменяемым.** Для массива это особенно заметно:

```java
record Numbers(long[] values) {}

// Следующие строки — внутри main:
long[] array = {10, 20};
Numbers numbers = new Numbers(array);
array[0] = 99;
System.out.println(numbers.values()[0]); // 99
```

Здесь `Numbers` хранит ссылку на тот же массив; автоматической копии нет. Поэтому `Snapshot` в лабораторной может быть `record`, но массив для снимка всё равно нужно копировать самостоятельно. Для примитивных компонентов, как `long count` и `long sum`, такой проблемы нет.

Для объектов `==` проверяет совпадение ссылок, а `equals` — равенство по правилам класса. У `record` автоматически сравниваются компоненты; если компонент — массив, он не начинает автоматически сравниваться по элементам.

**Мини-упражнение:** внутри `InterfaceDemo` объяви `record User(String name, int age) {}`. В `main` создай пользователя, выведи `name()` и `age()`, затем сравни через `equals` с другим `User` с теми же данными.

## 2. Запустить два потока и дождаться результата

Открой [S02Threads.java](src/practice/S02Threads.java).

```java
Thread first = new Thread(task, "first");
first.start();
first.join();
```

`new Thread(...)` создаёт объект потока, `start()` запускает выполнение его задачи, `join()` ждёт завершения. Это поведение определено в [API Thread](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Thread.html).

Поток — отдельное выполнение инструкций внутри той же программы. Объекты могут быть общими, но у каждого вызова метода свои локальные переменные. В примере каждый вызов `printSteps()` имеет собственный `i`.

`Runnable` — задача с методом `void run()`. Две записи означают здесь одно и то же:

```java
Runnable task = () -> printSteps();
Runnable otherTask = S02Threads::printSteps;
```

`() -> ...` — лямбда: «когда запросят выполнение задачи, выполни этот код». `::` — ссылка на готовый метод. Создание лямбды само по себе ничего не запускает.

Порядок строк между `first` и `second` может меняться. Внутри каждого потока числа идут по порядку. Даже если один поток успел напечатать всё первым, это допустимый запуск.

### Кто выполняет new Thread, start и join

Разберём именно запись, которая встретится в третьем упражнении:

```java
// Эти строки выполняет поток main:
Thread a = new Thread(S03Race::incrementMany);
a.start();
a.join();
System.out.println("Поток a завершился");
```

| Строка | Что делает main | Что происходит с a |
|---|---|---|
| `new Thread(S03Race::incrementMany)` | Создаёт объект и передаёт ему задачу «вызвать incrementMany» | Объект создан, задача ещё не выполняется |
| `a.start()` | Запускает поток и затем может продолжать свой код | Получает возможность выполнять задачу независимо от main |
| `a.join()` | Ждёт, если a ещё работает | Продолжает свою задачу; join не останавливает его |
| `println(...)` | Выполняет следующую строку после успешного join | Уже завершился |

`S03Race::incrementMany` — задача, а не результат вызова метода. Этот конструктор `Thread` принимает `Runnable`, поэтому Java понимает ссылку на метод как реализацию его `run()`. Запущенный поток вызывает задачу, а она — `incrementMany()`.

`start()` не ждёт завершения задачи. Рабочий поток может успеть выполнить часть работы или даже закончить её до следующей строки `main`, а может получить процессор позже. Поэтому нельзя рассуждать «строка после start точно выполнится раньше первой строки задачи».

`join()` ждёт **того потока, у которого вызван метод**, а приостанавливается **тот поток, который этот метод вызвал**. Если `a` уже завершился, ожидания не будет. Здесь используем `join()` без таймаута и предполагаем, что ожидающий поток не прервали. Вызов `join()` до `start()` не означает «подождать будущего запуска»: сначала запускай поток.

Обычно задача выполняется один раз: когда `incrementMany()` вернётся, закончится выполнение задачи и поток завершится. Чтобы делать работу долго, сама задача должна содержать цикл. Завершённый объект `Thread` повторно запустить нельзя.

Для двух одновременно работающих задач порядок такой:

```java
Thread a = new Thread(S03Race::incrementMany);
Thread b = new Thread(S03Race::incrementMany);
a.start();
b.start();
a.join();
b.join();
```

Пока `main` ждёт `a`, поток `b` тоже может работать и даже завершиться первым. Порядок `join()` не задаёт порядок исполнения рабочих потоков. После обоих ожиданий завершились оба.

Без `join()` следующие строки `main` могут выполниться до окончания рабочих задач. Это не значит, что рабочие немедленно погибнут при выходе из `main`: обычные потоки из наших примеров удерживают JVM работающей. Их называют недемон-потоками; демон-потоки — фоновые потоки, которые сами по себе не удерживают программу от завершения. Ожидание нужно, чтобы **код после него** мог использовать готовые результаты.

**Сделай сам:**

1. Замени `first.start()` на `first.run()`. Посмотри на имя потока в выводе. Обычный вызов `run()` выполняет код в вызывающем потоке.
2. Верни `start()`. Переставь команды в порядок `first.start(); first.join(); second.start(); second.join();`. Почему задачи теперь выполняются последовательно?
3. Добавь третий поток. Сначала запусти все три, потом дождись всех трёх.
4. Попробуй дважды вызвать `start()` у одного объекта и прочитай исключение. Для нового запуска нужен новый `Thread`.

`throws InterruptedException` у `main` пока позволяет не писать обработчик прерывания вокруг `join()`. У лямбды `Runnable` так не получится: её метод `run()` не объявляет это исключение; пример обработки будет в шаге 7.

### 2.1. Лямбда: передать действие, которое выполнят позже

В Java часто нужно передать другому коду **действие**: «когда понадобится, выполни вот эти инструкции». Для потока это его задача. В Java такую задачу можно представить объектом интерфейса `Runnable`. У него один абстрактный метод:

```java
// Это иллюстрация уже существующего java.lang.Runnable.
// Объявлять собственный Runnable в проекте не нужно.
public interface Runnable {
    void run();
}
```

Начнём с уже знакомого способа — отдельного класса. Создай `LambdaDemo.java`:

```java
package practice;

public class LambdaDemo {
    static class HelloTask implements Runnable {
        @Override
        public void run() {
            System.out.println("Привет из " + Thread.currentThread().getName());
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Runnable task = new HelloTask();
        Thread worker = new Thread(task, "worker");
        worker.start();
        worker.join();
    }
}
```

Здесь задача — объект `HelloTask`. `Thread` получает ссылку на него и при запуске выполняет его `run()` в новом потоке.

Если отдельный класс нужен только ради этого короткого действия, можно заменить строку `Runnable task = new HelloTask();` на:

```java
Runnable task = () -> {
    System.out.println("Привет из " + Thread.currentThread().getName());
};
```

Это и есть **лямбда-выражение**. Оно позволяет задать реализацию единственного абстрактного метода интерфейса без отдельного именованного класса. В этом примере поведение задачи осталось прежним.

Читай запись по частям:

- `Runnable task` — переменная с задачей; её тип подсказывает Java, какой метод мы реализуем;
- `()` — список параметров: у `Runnable.run()` их нет;
- `->` — отделяет параметры от тела;
- `{ ... }` — инструкции, которые будут выполнены **при вызове задачи**;
- `;` после закрывающей скобки завершает присваивание переменной.

Для одной подходящей инструкции фигурные скобки можно опустить:

```java
Runnable task = () -> System.out.println("Привет!");
```

Интерфейс с одним абстрактным методом называется **функциональным интерфейсом**. Лямбда подходит для такого интерфейса, потому что однозначно понятно, какой метод она реализует. `Runnable` подходит. Наш `Accumulator` с двумя абстрактными методами `add` и `total` — нет.

**Лямбда не создаёт поток.** Сначала выполни такой код в `main`:

```java
Runnable task = () -> System.out.println(Thread.currentThread().getName());
System.out.println("Задача создана");
task.run(); // обычный вызов: напечатает main
```

После присваивания ничего из тела лямбды ещё не выполнялось. Вызов `task.run()` выполнил её в текущем потоке. А теперь передай ту же задачу новому потоку:

```java
Thread worker = new Thread(task, "worker");
worker.start(); // задачу выполнит worker
worker.join();
```

Итак, `Runnable` описывает работу, а `Thread` предоставляет отдельный поток для её выполнения. Один и тот же объект задачи можно передать нескольким потокам: это не создаст автоматические копии данных, которыми пользуется задача.

### 2.2. Параметры лямбды, возвращаемое значение и запись ::

Лямбды применяются и без потоков. В интерфейсе `Sender` из раздела 1.1 один метод `send(String text)`, поэтому в `main` класса `InterfaceDemo` можно написать:

```java
Sender sender = text -> System.out.println(text);
sender.send("Привет!");
```

При вызове `send` строка попадёт в параметр `text`, затем выполнится тело лямбды. Тип `String` компилятор узнаёт из интерфейса. Для одного параметра скобки можно опустить: `text -> ...` и `(text) -> ...` здесь равнозначны.

Если метод возвращает число, лямбда должна его вернуть. Добавь внутрь `LambdaDemo` интерфейс, а строки использования — в `main`:

```java
@FunctionalInterface
interface Operation {
    int apply(int x);
}

// Внутри main:
Operation twice = x -> x * 2;
System.out.println(twice.apply(5)); // 10
```

`x -> x * 2` возвращает результат выражения. Более длинная запись того же действия — `x -> { return x * 2; }`. Аннотация `@FunctionalInterface` необязательна, но попросит компилятор проверить, что абстрактный метод действительно один.

В твоём `S02Threads` встречается ещё одна короткая форма:

```java
Runnable task = () -> printSteps();
Runnable otherTask = S02Threads::printSteps;
```

Здесь обе записи задают действие «вызови уже существующий статический метод `printSteps` без аргументов». `::` — **ссылка на метод**, а не его немедленный вызов. Поэтому `new Thread(S02Threads::printSteps)` допустим, а `new Thread(printSteps())` — нет: во втором случае метод вызывается сразу и возвращает `void`, который нельзя передать как задачу.

Лямбда также может использовать переменные окружающего кода:

```java
String name = "Аня";
Runnable greeting = () -> System.out.println("Привет, " + name);
greeting.run();
```

Такое использование называется **захватом переменной**. Захваченной локальной переменной нельзя присвоить новое значение: она должна быть `final` или просто не меняться после инициализации. При этом, если она хранит ссылку на изменяемый объект, сам объект менять можно. Его потокобезопасность лямбда не обеспечивает.

**Закрепи на своём втором упражнении:**

1. Замени одну лямбду отдельным классом `implements Runnable`, как `HelloTask` выше.
2. Другую задачу оставь лямбдой, третью запиши через `S02Threads::printSteps`.
3. Убедись, что все три способа позволяют выполнить задачу в потоке.
4. Объясни своими словами: что задаёт интерфейс, что задаёт лямбда и что делает `start()`.

После этого переходи к счётчику из шага 3: основная Java-запись вокруг потоков уже разобрана.

## 3. Увидеть гонку на общем счётчике

Запусти [S03Race.java](src/practice/S03Race.java) несколько раз. Два потока делают по миллиону `counter++`. Ожидаемый математический итог — 2 000 000, но программа может напечатать меньше. Иногда она выдаст правильное число — это не исправляет ошибку.

Поле `static int counter` здесь одно на класс и общее для двух задач. Слово `static` **не делает его потокобезопасным**. Поле обычного объекта тоже будет общим, если передать обоим потокам один объект.

Почему локальный `i` в цикле не вызывает ту же проблему? Каждый вызов `incrementMany()` имеет собственную локальную переменную `i`. А обращение к полю `counter` из обоих вызовов ведёт к одной общей переменной. Java не копирует поля класса или объекты при запуске потока.

Даже локальные переменные могут содержать ссылки на общий объект. Например, два разных параметра метода могут указывать на один массив. Поэтому спрашивай не только «где объявлена переменная?», но и «какие именно данные меняются и кто ещё до них доберётся?».

Для понимания раскладывай `counter++` на три действия: прочитать, прибавить, записать. Пример потерянного обновления:

| Шаг | Поток A | Поток B |
|---|---|---|
| 1 | Прочитал 0 | |
| 2 | | Прочитал 0 |
| 3 | Записал 1 | |
| 4 | | Записал 1 |

Два вызова дали прибавку 1. Реальный машинный код может отличаться; главное — у обычного `++` нет гарантии атомарного обновления.

`join()` уже стоит в правильном месте. Он позволяет прочитать результат после завершения потоков, но не возвращает потерянные прибавления.

**Сделай сам:**

1. Запусти ту же работу одним потоком и проверь ожидаемый итог.
2. Добавь `volatile` к `counter`: `private static volatile int counter;`. **`volatile` — пометка поля для обмена значением между потоками: изменение нельзя бесконечно игнорировать, используя старое значение. Она не объединяет несколько действий в одно.** Поэтому чтение, прибавление и запись внутри `counter++` всё ещё могут пересекаться с действиями другого потока. Повтори запуски: гарантии правильного `++` всё ещё нет. Пример с флагом — в шаге 5.
3. Не вставляй `println` внутрь миллиона итераций: вывод меняет расписание и может скрыть ошибку.
4. Если гонка не проявляется на твоей машине, всё равно объясни таблицу выше. В шаге 9 будет пример ошибки, которую мы воспроизведём намеренно и стабильно.

## 4. Защитить данные с помощью synchronized

Открой [S04Monitor.java](src/practice/S04Monitor.java). Теперь ожидаемый результат — ровно 200 000.

```java
private final Object lock = new Object();

void increment() {
    synchronized (lock) {
        value++;
    }
}
```

У объекта `lock` есть **монитор** — встроенный замок, который может удерживать только один поток за раз. **Лок** (от английского lock) — блокировка; так мы называем этот замок. Код внутри защищённого блока называют **критической секцией**. Только один поток одновременно выполняет код, удерживая этот монитор. Для защиты нужны **один и тот же объект лока** и единый договор: все конкурирующие обращения к этим данным используют его. Освобождение и последующий захват этого монитора также обеспечивают видимость записей. [Правила Java](https://docs.oracle.com/javase/specs/jls/se21/html/jls-17.html).

В примере оба потока получили ссылку на один `Counter`. Если создать каждому свой, получатся два независимых счётчика.

Сам `lock` — обычный объект, который мы выбрали для согласования доступа. Он не содержит защищаемый счётчик и не знает о поле `value`. Именно конструкция `synchronized (lock)` связывает выполнение этого блока с монитором объекта. Если монитор занят, пришедший поток ждёт возможности войти; после освобождения сможет продолжить. Порядок, в котором ожидающие получат доступ, здесь не гарантирован.

Поток, который вообще не использует этот монитор, всё ещё может обратиться к `value`, если код ему это позволяет. Поэтому лок защищает данные только при соблюдении общего правила доступа всеми участниками.

Эквивалентный по идее синтаксис для лока на текущем объекте:

```java
synchronized void increment() {
    value++;
}
```

Это блокировка на `this`. У `static synchronized` метода локом будет объект класса, а не конкретный экземпляр. Если переписываешь пример на синхронизированные методы, переведи **оба метода** на один монитор.

**Сделай сам:**

1. Перепиши `increment()` и `get()` как `synchronized`-методы, убери отдельный `lock`.
2. Верни исходную версию и замени `synchronized (lock)` на `synchronized (new Object())` в записи. Почему это не защищает общий счётчик?
3. Добавь в класс поле `sum` и метод `add(long value)`, который увеличивает число вызовов и сумму. Какие действия должны попадать в одну критическую секцию?
4. Добавь метод, возвращающий пару «число вызовов + сумма», и подумай, почему читать эти поля двумя независимыми защищёнными вызовами недостаточно для единого снимка.

В лабораторной этап 1 требует именно `synchronized`. Возврат или исключение внутри блока освобождают монитор автоматически.

## 5. Остановить работающий поток: volatile и join

Открой [S05StopFlag.java](src/practice/S05StopFlag.java).

**`volatile` читается «волатайл».** Это ключевое слово перед типом поля. Оно нужно, когда один поток меняет поле, а другой должен видеть это изменение. **Флаг** — поле с двумя значениями, `true` и `false`, которым передают условие или сигнал; у нас это просьба остановиться.

```java
private static volatile boolean stop;
```

Главный поток меняет флаг, рабочий читает его в цикле. Вот смысл кода из примера:

```java
// Рабочий поток:
while (!stop) { // пока не попросили остановиться
    local++;
}

// Главный поток, отдельно:
stop = true;   // передаёт просьбу остановиться
```

Без `volatile` нет гарантии, что рабочий поток заметит новое значение: JVM может, например, повторно использовать ранее прочитанное `false`. С `volatile` чтения флага должны соблюдать правила обмена между потоками. Когда рабочий поток после записи `true` снова проверяет флаг, он выходит из цикла. Это не обещание остановки за заданное число миллисекунд: рабочему потоку ещё нужно получить время процессора.

В исходном примере `result` обычный: его пишет один рабочий поток, а главный читает только после `join()`. Дополнительная пометка `volatile` для этого результата не нужна.

Почему тогда `volatile counter` не исправляет `counter++`? Два потока всё ещё могут прочитать одно и то же число `5`, каждый прибавить единицу и каждый записать `6`. Видимость есть, но два увеличения дали результат одного. Для такого счётчика нужны `synchronized` или атомарная операция из шага 6.

Здесь рабочий поток останавливает себя сам: замечает `stop == true`, выходит из `while`, записывает результат и доходит до конца задачи. Строка `stop = true` не обрывает его выполнение посередине инструкции. Такой способ называется согласованной, или кооперативной, остановкой.

`volatile` не создаёт очередь и не заставляет читателя ждать. Он задаёт правила видимости и порядка обращений к полю. Формулировка «всегда читает прямо из оперативной памяти» слишком грубая: Java гарантирует поведение программы, а конкретные действия процессора зависят от JVM и архитектуры.

Разделяй три задачи:

| Что нужно | Чем решаем в упражнениях |
|---|---|
| Передать изменение флага | `volatile boolean` |
| Не терять общий инкремент | `synchronized` или `AtomicLong.incrementAndGet()` |
| Получить связанные поля как единое состояние | Общий лок или специально разработанный протокол |

`Thread.sleep(200)` лишь отмеряет приблизительное время работы. Он не гарантирует, что другой поток уже что-либо сделал, и не заменяет синхронизацию. `join()` создаёт гарантию видимости действий завершившегося потока; `sleep()` такой гарантии не даёт. [Спецификация](https://docs.oracle.com/javase/specs/jls/se21/html/jls-17.html).

**Сделай сам:** убери `volatile` и повтори эксперимент. Программа может закончить работу, а может зависнуть. Если зависла, останови красной кнопкой Stop в IDEA или `Ctrl+C` в терминале. Затем верни `volatile`. Не используй такой запуск как доказательство, что обычный флаг безопасен.

Другой способ отмены — `interrupt()`: запрос потоку завершиться. Цикл может проверять `Thread.currentThread().isInterrupted()`. Это не принудительное убийство потока. Методы ожидания вроде `sleep()` и `await()` могут ответить `InterruptedException`.

## 6. Атомарный счётчик и CAS — по шагам

Открой [S06Atomics.java](src/practice/S06Atomics.java). Здесь четыре потока, итоговые `count=40000`, `max=39999`. Сначала разберём счётчик, потом максимум.

### Что значит «атомарная операция»

**Это действие, которое для других потоков выполняется как одно целое.** Они не могут вмешаться в его середину и испортить результат.

Вспомни обычное `count++`. Для понимания разбей его на три шага:

1. Прочитать число, например `5`.
2. Прибавить единицу: получить `6`.
3. Записать `6` обратно.

Два потока могут оба прочитать `5` и оба записать `6`. Хотя каждый хотел прибавить единицу, получили `6` вместо `7`.

У Java есть готовый класс `AtomicLong` — объект, который хранит число типа `long` и умеет безопасно менять его из разных потоков:

```java
AtomicLong count = new AtomicLong(5); // внутри число 5
count.incrementAndGet();            // прибавить 1 как одно целое
System.out.println(count.get());    // прочитать: 6
```

Если два потока вызовут `incrementAndGet()` по одному разу, из `5` получится **7**. Оба увеличения будут учтены. Самому писать `synchronized` вокруг этого вызова не нужно.

Запомни три метода:

| Запись | Что делает |
|---|---|
| `count.get()` | Прочитать число |
| `count.set(10)` | Записать число 10 |
| `count.incrementAndGet()` | Увеличить на 1 и вернуть новое число одним действием |

Вот так безопасное увеличение **не получится**:

```java
count.set(count.get() + 1);
```

Здесь чтение и запись — отдельные действия. Между ними другой поток может успеть изменить число. Дело не в количестве строк: важна операция, которую ты вызываешь.

`AtomicLong` нужно импортировать из `java.util.concurrent.atomic`. Если перед переменной написано `final`, нельзя заменить сам объект другим; менять число внутри через его методы можно.

### Что такое CAS

CAS — короткое название действия **«сравни и замени»**. В Java метод называется `compareAndSet`.

```java
AtomicLong number = new AtomicLong(5);
boolean changed = number.compareAndSet(5, 8);
```

Прочитай последнюю строку так: **«Если сейчас внутри 5, замени на 8. Иначе ничего не меняй»**.

- Первый аргумент `5` — число, которое ты ожидаешь увидеть.
- Второй аргумент `8` — число, которое хочешь записать.
- Результат `true` — замена произошла; `false` — число не совпало, замены не было.

Проверка и замена здесь выполняются **как одно целое**. Именно этим метод отличается от двух отдельных вызовов:

```java
// Плохая замена CAS: между проверкой и записью есть промежуток.
if (number.get() == 5) {
    number.set(8);
}
```

В этом промежутке другой поток мог записать `20`, а мы затёрли бы его своей восьмёркой.

### Зачем CAS нужен для максимума

Представь, что общее поле хранит самое большое увиденное число. Сейчас там `10`.

1. Поток A хочет предложить `15`. Читает текущий максимум: `10`.
2. Поток B успевает записать новый максимум: `20`.
3. Если A просто запишет `15`, максимум ошибочно уменьшится с `20` до `15`.

Поэтому A делает `maximum.compareAndSet(10, 15)`: «замени на 15, только если там всё ещё 10». Сейчас там 20, поэтому метод вернёт `false` и сохранит 20.

После неудачи A должен **ещё раз прочитать число и решить, нужна ли замена**. Это делает цикл в упражнении:

```java
static void offerMaximum(long candidate) { // candidate — предложенное число
    while (true) {                       // повторять попытки
        long old = maximum.get();        // что записано сейчас?
        if (candidate <= old) {
            return;                      // наше число не больше: делать нечего
        }
        if (maximum.compareAndSet(old, candidate)) {
            return;                      // получилось записать: закончили
        }
        // Не получилось: возвращаемся к началу цикла и снова читаем число.
    }
}
```

Почему недостаточно просто выйти после неудачи? Допустим, A предлагал `30`, а B записал `20`. Первая попытка A не удалась, но его число всё ещё больше — нужна новая попытка.

CAS сравнивает текущее число, а не историю его изменений. Для нашего примера с растущим максимумом этого достаточно.

### Что означает final int id = k

Внизу файла цикл создаёт четыре потока. Для каждого нужно запомнить его номер:

```java
final int id = k;
```

`k` меняется при переходе к следующей итерации. А `id` — отдельная копия номера для задачи, созданной на этой итерации. Лямбда может использовать такую локальную переменную, потому что после присваивания её значение больше не меняется.

### Попробуй сам

1. В отдельном `main` создай число `5`. Вызови `compareAndSet(5, 8)`, затем `compareAndSet(5, 12)`. После каждого вызова напечатай результат вызова и число. Ожидается сначала `true` и `8`, затем `false` и `8`.
2. В `S06Atomics` замени `incrementAndGet()` на `count.set(count.get() + 1)`. Запусти несколько раз: результат может оказаться меньше ожидаемого. После этого верни правильный вызов.
3. Перечитай историю про максимум 10, 15 и 20 и сопоставь её со строками `offerMaximum`.
4. Когда максимум станет понятен, напиши похожий метод для минимума. Какое начальное значение ему нужно?

Пока достаточно понимать `get`, `set`, `incrementAndGet` и `compareAndSet`. Более сложные методы чтения и записи разберём там, где они понадобятся в лабораторной.

## 7. Потоки ждут команды «можно начинать»

**Задача этого пункта:** запустить несколько потоков, но разрешить им считать только после общего сигнала. Потом дождаться результатов и сложить их.

Не нужно сразу разбирать весь `S07StartGate`. Начни с маленького [S07Door.java](src/practice/S07Door.java): в нём только один рабочий поток и один сигнал.

### Сначала один поток и одна «дверь»

`CountDownLatch` — готовый класс Java. Представляй его как дверь со счётчиком. Пока счётчик больше нуля, дверь закрыта. Когда он стал нулём — дверь открылась и больше не закрывается.

```java
CountDownLatch start = new CountDownLatch(1);
```

Создали закрытую дверь: счётчик равен 1. Имя `start` придумали мы сами.

Нужны только два метода:

| Код | Простыми словами |
|---|---|
| `start.await()` | «Ждать здесь, пока счётчик не станет нулём» |
| `start.countDown()` | «Уменьшить счётчик на 1»; переход с 1 на 0 открывает дверь |

Если дверь уже открыта, `await()` пропускает поток дальше без ожидания. Сигнал не потеряется, даже если его дали раньше, чем поток подошёл к двери.

Вот вся маленькая программа:

```java
package practice;

import java.util.concurrent.CountDownLatch;

public class S07Door {
    public static void main(String[] args) throws InterruptedException {
        CountDownLatch start = new CountDownLatch(1);

        Thread worker = new Thread(() -> {
            System.out.println("Рабочий: жду разрешения");
            try {
                start.await();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
            System.out.println("Рабочий: выполняю задачу");
        });

        worker.start();
        System.out.println("Главный: разрешаю работать");
        start.countDown();
        worker.join();
        System.out.println("Главный: рабочий закончил");
    }
}
```

Прочитай по порядку действий:

1. `main` создаёт дверь и рабочий поток.
2. `worker.start()` запускает рабочий поток. Он может дойти до `await()` и ждать там.
3. `main` вызывает `start.countDown()`: было 1, стало 0. Дверь открыта.
4. Рабочий проходит через `await()` и выполняет задачу.
5. `worker.join()` позволяет `main` дождаться конца рабочего.

`main` может успеть открыть дверь ещё до прихода рабочего. Поэтому строки «жду разрешения» и «разрешаю работать» могут печататься в разном порядке. Но строка «выполняю задачу» появится после «разрешаю работать», а «рабочий закончил» — последней.

**Не путай два действия:** `worker.start()` запускает поток, а `start.countDown()` разрешает ему пройти дальше в уже запущенной задаче. `start` в этих записях — имя метода в первом случае и имя переменной во втором.

### Почему вокруг await написано try / catch

Ожидающий поток могут попросить прекратить ожидание. Тогда `await()` сообщает об этом через `InterruptedException`. Это название исключения — особого сигнала, который меняет обычный ход выполнения кода.

- `try { ... }` — выполняем код, который может сообщить о такой ситуации.
- `catch (...) { ... }` — что делать, если она произошла.
- `Thread.currentThread().interrupt()` — восстанавливаем у текущего потока отметку «его попросили прерваться»: при выбрасывании этого исключения она сбрасывается.
- `return` — заканчиваем задачу, вместо того чтобы продолжать её без разрешения.

В обычном запуске никто не прерывает рабочего, поэтому `catch` не выполняется. Пока достаточно понимать назначение этих строк.

### Теперь четыре потока: S07StartGate

Открой [S07StartGate.java](src/practice/S07StartGate.java). В нём уже **два отдельных счётчика**, каждый со своей задачей:

```java
CountDownLatch ready = new CountDownLatch(4);
CountDownLatch start = new CountDownLatch(1);
```

`ready` отвечает на вопрос **«все четыре рабочих дошли до точки готовности?»**. Каждый рабочий один раз делает `ready.countDown()`:

```text
Пришёл первый:   4 → 3
Пришёл второй:   3 → 2
Пришёл третий:   2 → 1
Пришёл четвёртый: 1 → 0
```

Главный поток вызывает `ready.await()`. Он ждёт нуля, то есть всех четырёх сообщений о готовности. После этого открывает другую дверь — `start`.

| Рабочие потоки | Главный поток main |
|---|---|
| Каждый сообщает: `ready.countDown()` | Ждёт всех: `ready.await()` |
| Каждый ждёт: `start.await()` | Разрешает считать: `start.countDown()` |
| Каждый считает свою часть | Ждёт завершения всех через `join()` |
| Каждый сохраняет свой ответ | Складывает готовые ответы |

Зачем два счётчика? Один собирает сообщения **от рабочих к главному**, другой передаёт разрешение **от главного к рабочим**. Это позволяет всем начать подсчёт после общего разрешения. Начало не обязано совпасть до наносекунды: процессор всё равно распределяет время между потоками.

### Куда каждый поток записывает ответ

```java
long[] results = new long[4];
```

Это четыре места для результатов. Сначала все равны нулю.

```java
long local = 0;
for (int i = 0; i < 100_000; i++) {
    local++;
}
results[id] = local;
```

У каждого вызова задачи **своя переменная `local`**. Потоки не увеличивают одно общее число. Закончив, каждый кладёт ответ в своё место: `results[0]`, `results[1]`, `results[2]` или `results[3]`.

После всех `join()` массив выглядит так:

```text
[100000, 100000, 100000, 100000]
```

Главный складывает числа и получает **400000**. `AtomicLong` тут не нужен: одно место в массиве записывает только один рабочий, а главный читает после завершения рабочих.

`Thread[] threads` — другой массив: в нём хранятся сами объекты потоков, чтобы потом вызвать у каждого `join()`. `final int id = k` запоминает номер места для конкретной задачи.

**Попробуй по одному изменению:**

1. Запусти `S07Door`. Найди строку, которая даёт разрешение, и строку, которая ждёт.
2. Запусти `S07StartGate`. Замени 100 000 повторений на 10. Итог должен быть 40. Подпись `expected` тоже измени.
3. Поставь два рабочих вместо четырёх. Теперь итог должен быть 20.
4. Когда это понятно, раздели маленькую сумму: первый поток складывает числа 1–5, второй — 6–10. Их ответы 15 и 40, общий ответ 55. Затем увеличивай задачу.

**Для лабораторной пригодится:** разрешить рабочим старт, дать им поработать, остановить флагом `stop`, дождаться и сложить число сделанных вызовов. Само измерение скорости разберём позже.

## 8. ThreadLocal: каждому потоку своё число

**Идея:** вместо одного счётчика, за который спорят все, выдаём каждому свой. В конце складываем ответы.

В пункте 7 мы уже сделали это обычными локальными переменными. `ThreadLocal` нужен, когда личные данные хочется получать из разных методов по одному общему имени, не передавая их каждый раз параметром.

Открой [S08ThreadLocal.java](src/practice/S08ThreadLocal.java). Начни с этого класса:

```java
static final class State {
    long count;
}
```

`State` — придуманное нами имя. Это обычный объект с одним числом `count`, изначально 0. Слово «состояние» здесь означает просто данные, которые мы храним.

Теперь:

```java
ThreadLocal<State> local = ThreadLocal.withInitial(() -> new State());
```

Читай так: **«Когда поток впервые попросит свои данные, создай для него новый State»**.

```java
State mine = local.get();
```

Читай так: **«Дай данные того потока, который сейчас выполняет эту строку»**.

Что получится:

| Кто вызывает local.get() | Что получает |
|---|---|
| Поток A первый раз | Новый объект A с `count = 0` |
| Поток A второй раз | Тот же объект A |
| Поток B первый раз | Другой, новый объект B с `count = 0` |

Поэтому, когда A делает `mine.count++`, число внутри объекта B не меняется. Это работает потому, что лямбда создаёт **новый** `State`. `ThreadLocal` сам объекты не копирует.

### Зачем в полном примере есть ещё список states

Главному потоку нужны все ответы. Но `local.get()` в `main` выдаст личные данные **main**, а не рабочего A или B.

Поэтому при создании каждого `State` кладём ссылку на него в общий список:

```java
State state = new State();
synchronized (listLock) {
    states.add(state);
}
return state;
```

`states.add(state)` не копирует объект. Теперь и рабочий, и список содержат ссылку на один и тот же `State`. Это как сохранить адрес, по которому потом можно найти ответ.

Сам список общий, и потоки могут одновременно добавлять в него записи. Поэтому добавление делаем по очереди под одним замком `listLock`.

После всех `join()` главный проходит по списку и складывает `state.count`. Четыре потока по 100 000 дают 400 000.

**Почему обычное count++ здесь допустимо?** Каждый объект меняет только его рабочий поток. Главный начинает читать лишь после окончания работы. Если читать во время записи, понадобятся дополнительные правила — это будет в лабораторной.

`local.remove()` означает «забудь привязку личных данных к текущему потоку». Объект при этом остаётся доступен через наш список. Следующий `get()` после `remove()` снова создаст данные. Поэтому в лабораторной нельзя делать `remove()` после каждой записи: потеряется смысл одного личного накопителя.

**Попробуй:** внутри задачи, до `remove()`, выведи `local.get() == local.get()`. Должно быть `true`: один поток дважды получает свой же объект. Потом добавь в `State` ещё поле `sum` и собери его значения после `join()`.

## 9. Два правильных числа могут дать неправильную пару

**Идея:** безопасно изменить одно число — ещё не значит безопасно изменить сразу два.

Представь два счётчика, `left` и `right`. Одна задача должна увеличить оба:

```java
left.incrementAndGet();
right.incrementAndGet();
```

Сначала было `0, 0`, после полной задачи должно стать `1, 1`. Но это **два отдельных вызова**. Между ними программа находится в состоянии `1, 0`.

Если другой поток прочитает числа именно в этот момент, он увидит половину выполненной задачи. Даже несмотря на то, что каждый счётчик — `AtomicLong` и ни одно увеличение не потерялось.

Открой [S09SplitSnapshot.java](src/practice/S09SplitSnapshot.java). В нём мы специально останавливаем запись посередине, чтобы увидеть это своими глазами:

| Шаг | Рабочий поток writer | Главный поток main |
|---|---|---|
| 1 | Увеличивает `left`: теперь `1, 0` | Ждёт `halfway.await()` |
| 2 | Вызывает `halfway.countDown()`: «половина готова» | Получает разрешение продолжить |
| 3 | Ждёт на `continueWriting.await()` | Печатает `1, 0` |
| 4 | Получает разрешение продолжить | Вызывает `continueWriting.countDown()` |
| 5 | Увеличивает `right`: теперь `1, 1`, заканчивает | Ждёт через `writer.join()`, затем печатает `1, 1` |

Ожидаемый вывод:

```text
During update: left=1, right=0
After join: left=1, right=1
```

`halfway` и `continueWriting` — такие же двери со счётчиком 1, как в пункте 7. Они нужны только для демонстрации точного порядка действий.

**Снимок** — данные, которые мы прочитали и сохранили для просмотра. Хороший снимок должен содержать числа, подходящие друг к другу. Например, если записаны три покупки, общая сумма должна включать эти же три покупки, а не только две.

Для лабораторной это ключевая мысль: `AtomicLong` защищает отдельное изменение, но не гарантирует правильную пару «количество + сумма» при чтении во время записи.

**Попробуй:** в отдельной программе используй один общий замок вокруг увеличения двух чисел и тот же замок вокруг чтения пары. Не оставляй ожидание разрешения внутри замка: иначе рабочий может ждать главного, а главный — замка рабочего. Оба остановятся. Такое взаимное ожидание называется **deadlock**, или взаимная блокировка.

## 10. По желанию: ждать, пока появится сообщение

Этот пункт можно пропустить до лабораторной. Здесь ещё один способ ожидания: **«сообщения пока нет — подожди; появилось — забери»**.

Открой [S10WaitNotify.java](src/practice/S10WaitNotify.java). `Mailbox` — наш класс, название означает «почтовый ящик». Внутри одна строка:

```java
private String message;
```

Сначала она равна `null`: сообщения нет.

Главный поток вызывает:

```java
synchronized void put(String value) {
    message = value;
    notifyAll();
}
```

Он получает замок объекта, сохраняет сообщение и вызывает `notifyAll()`: «все, кто ждёт на этом объекте, попробуйте продолжить». Только когда метод отпустит замок, ожидающий сможет получить его и продолжить.

Рабочий вызывает `take()`. Самая важная часть:

```java
while (message == null) {
    wait();
}
```

Читай так: «Пока сообщения нет, ждать». `wait()` временно **отпускает замок**, чтобы другой поток смог войти в `put()` и положить сообщение. Перед продолжением `wait()` снова получает тот же замок.

Почему `while`, а не `if`? Проснуться не означает «сообщение точно есть». Например, его мог уже забрать другой ожидающий. Поэтому проверяем ещё раз.

Остальные строки `take()`:

```java
String result = message; // запомнить сообщение
message = null;          // отметить, что ящик пуст
return result;           // вернуть сообщение тому, кто вызвал take
```

В примере отправляется ровно одно сообщение. Две отправки подряд до чтения могут затереть первую: полноценную очередь мы здесь ещё не написали.

Чтобы не путаться в ожиданиях:

| Метод | Чего ждём |
|---|---|
| `worker.join()` | Рабочий поток закончит задачу |
| `start.await()` | Счётчик CountDownLatch станет нулём |
| `wait()` | Нас разбудят; после пробуждения заново проверяем своё условие |
| `Thread.sleep(200)` | Примерно 200 миллисекунд пройдёт |

`wait()` вызывают, уже удерживая замок того же объекта, например внутри его `synchronized`-метода. `sleep()` замок не отпускает и сам по себе не помогает безопасно обмениваться данными.

Если `put()` выполнился до прихода читателя, `take()` увидит готовое сообщение и не станет ждать. Работает сохранённое значение `message`, а не память об уведомлении.

**Попробуй позже:** сделай так, чтобы второй `put()` ждал, пока первое сообщение заберут. После `take()` нужно сообщать ожидающим, что место освободилось. Пока для перехода к лабораторной достаточно понимать пункты 7–9.

## 11. Лабораторная: сначала однопоточная логика

Дальше держи рядом [lab1/README.md](../lab1/README.md). Там требования преподавателя и таблицы, которые нужно заполнить.

**Что вообще пишем:** объект, которому передают числа, а он считает их количество, сумму, минимум и максимум. Он называется **коллектор метрик**: «метрики» здесь — числа с длительностью запросов, а «коллектор» их собирает.

Например, передали `4`, `8`, `12`. Должно получиться: три записи, сумма 24, минимум 4, максимум 12. Сначала сделаем это в одном потоке. Потом несколько потоков будут передавать числа одному объекту одновременно.

Два главных метода:

| Метод | Что просим сделать |
|---|---|
| `record(8)` | «Учти ещё одно число: 8» |
| `snapshot()` | «Верни копию накопленных результатов» |

**Не пиши все этапы сразу.** Сначала только количество и сумма в одном потоке. Когда они проверены — добавляй следующее поле.

### Как потоки и коллектор связаны в Java

Коллектор — обычный объект с методами и полями. По нашей схеме он сам не создаёт потоки. Их создаёт замерялка и передаёт задачам ссылку на **один экземпляр** коллектора:

```java
// Иллюстрация для будущего Bench: классы коллектора ты ещё напишешь.
MetricsCollector collector = new LockedCollector();
Runnable work = () -> collector.record(7);
Thread a = new Thread(work);
Thread b = new Thread(work);
a.start();
b.start();
a.join();
b.join();
Snapshot result = collector.snapshot();
```

Здесь каждый рабочий вызывает `record(7)` один раз, поэтому ожидается две записи. Для нагрузки внутри задачи появится цикл. Методы `record` одновременно исполняются разными потоками, но работают с одним объектом; отсюда необходимость синхронизации. `snapshot()` в последней строке выполняет главный поток, потому что именно он его вызвал.

Если перенести `new LockedCollector()` внутрь задачи, каждый вызов задачи создаст свой коллектор. Тогда потоки перестанут записывать в общее состояние, и получится другой эксперимент. На этапе с `ThreadLocal` экземпляр коллектора остаётся общим, а личные состояния создаются уже внутри него.

Создай `lab1/src`, отметь как **Sources Root**. Внутри создай пакет `lab1`, а в нём классы. Например:

```text
lab1/src/lab1/
  MetricsCollector.java
  Snapshot.java
  SequentialCollector.java
  LockedCollector.java
  StripedCollector.java
  ThreadLocalCollector.java
  DoubleBufferedCollector.java
  Bench.java
  ConsistencyCheck.java
```

Это предлагаемые имена, а не уже созданное решение. В каждом файле будет `package lab1;`. Объявления `MetricsCollector` и `Snapshot` возьми из задания: это заданный контракт, его не нужно изобретать.

Пока можно создать `ManualCheck` с обычным `main` и проверками:

```java
if (actual != expected) {
    throw new AssertionError("expected=" + expected + ", actual=" + actual);
}
```

Эта проверка всегда активна. Ключевое слово `assert` потребовало бы запуска с `-ea`. JUnit на этом этапе не нужен.

### Этап 0а. Коллектор в одном потоке

Кроме количества и суммы, в задании есть **корзины**. Корзина — счётчик чисел из определённого диапазона: в первую попадают 0–3, во вторую 4–7, в третью 8–11. Например, число 6 увеличивает вторую корзину на 1. Все 256 корзин вместе называют **гистограммой** — она показывает, каких значений много, а каких мало.

**p50 и p99** помогают описать задержки. Представь все записи, отсортированные от маленькой к большой: p50 указывает место, до которого дошла половина записей, p99 — 99%. В лабораторной у нас только корзины, поэтому возвращаем приблизительное значение — нижнюю границу нужной корзины. Ниже есть пример с пятью числами.

Делай в таком порядке:

1. `count` и `sum`, затем метод `record(long value)`.
2. Добавь `min` и `max`. Подумай о значениях до первой записи.
3. Добавь `long[256]` и вычисление номера корзины.
4. Напиши `snapshot()`, который копирует корзины и сводку.
5. Добавь вычисление p50 и p99 по скопированным данным.

Полезный синтаксис, без реализации коллектора:

```java
int bucket = (int) Math.min(value / 4, 255);
long[] copy = buckets.clone();
```

Для массива примитивных `long` такой копии достаточно. `record Snapshot(long[] buckets, ...)` сам по себе массив **не копирует**. Его метод чтения (accessor) `buckets()` тоже отдаёт ссылку. Минимальное требование: изменение полученного снимка не должно менять внутренние корзины коллектора. Старый снимок не должен изменяться от новых записей.

Для пустого снимка задание не фиксирует весь контракт. Явно выбери и запиши соглашение: например `count=0`, `sum=0`, нулевые корзины, `min=max=p50=p99=0`. Внутренний `min` при этом может оставаться `Long.MAX_VALUE` до первой записи. Среднее при пустом наборе обрабатывай отдельно.

Диапазон учебной нагрузки неотрицательный. Значения от 1024 отправляй в последнюю корзину, но в `sum/min/max` сохраняй настоящее значение. Для отрицательных значений можно явно выбрасывать `IllegalArgumentException`; не допускай случайного отрицательного индекса.

**Контрольные данные:**

| Записи | Что проверить |
|---|---|
| Нет записей | Выбранный контракт пустого снимка |
| `0, 3, 4, 7, 8` | `count=5`, `sum=22`, `min=0`, `max=8` |
| Те же | Корзины 0, 1, 2 равны 2, 2, 1; остальные нули |
| Те же | `p50=4`, `p99=8`; среднее `4.4` |
| `1023, 1024, 5000` в новом коллекторе | В корзине 255 три записи; `sum=7047`, `max=5000`; перцентили по этой корзине равны 1020 |
| Снимок, затем ещё запись | Старый снимок не меняется |
| Изменение `snapshot.buckets()[0]` | Следующий снимок коллектора от этого не меняется |

Перцентиль здесь приблизительный: возвращается нижняя граница корзины, поэтому он может быть ниже `min`, например для единственного значения `3` результат равен `0`.

Как найти нужную корзину: посчитай, до какой записи нужно дойти, затем складывай содержимое корзин слева направо. Для p50 из пяти записей нужно дойти до третьей: половина от 5 — 2.5, округляем вверх до 3. Для p99 нужно дойти до пятой.

В примере `0, 3, 4, 7, 8` в первой корзине две записи — третья ещё не встретилась. После второй корзины уже четыре — значит, третья находится в ней. Возвращаем её нижнюю границу: 4.

В Java округление вверх делает `Math.ceil(...)`. Для пустого набора поиск не запускай. Позже при очень больших числах учти, что у `long` есть предел, а дробные числа `double` хранятся приблизительно.

**Не переходи к потокам, пока все эти проверки не проходят.** Иначе ошибка формулы станет выглядеть как ошибка синхронизации.

### Этап 0б. Генератор и замерялка

Здесь две отдельные задачи. **Генератор** заранее создаёт массив чисел для записи. **Замерялка** выясняет, сколько вызовов `record()` успевают сделать потоки за секунду. Числа готовим заранее, чтобы не включать время их создания в скорость коллектора.

Сначала сделай генератор `long[] values`, отдельно от таймера. По заданию размер — `1 << 20` (это 2 в степени 20, то есть 1 048 576 элементов), значения `1..1023`, фиксированный seed (начальное число генератора, позволяющее повторить ту же последовательность) и веса `1 / k^1.15`.

В задании числа должны встречаться не одинаково часто: маленькие — чаще, большие — реже. Такое распределение здесь называют **распределением Ципфа**. Можно представить лотерею: у маленьких чисел больше билетов, поэтому их чаще вытягивают.

Сначала отладь коллектор на готовом маленьком массиве. Когда дойдёшь до настоящих замеров, сделай генератор по этим шагам:

1. Посчитай веса `w[k] = 1.0 / Math.pow(k, 1.15)`.
2. Сложи веса. Затем каждый вес раздели на общую сумму: получатся вероятности. Складывай эти вероятности по очереди и сохраняй промежуточные суммы в массив. Его называют CDF; последний элемент должен получиться около 1.
3. `random.nextDouble()` выдаёт число от 0 включительно до 1 не включительно. Назови его `u`. Найди первое место `k`, где накопленная вероятность больше `u`: это выбранное значение.
4. Сохрани `k` в `values`. Последнее значение CDF удобно явно сделать `1.0` против погрешности округления.

Сначала ищи нужное место обычным циклом слева направо: этот поиск выполняется до замера скорости. Используй `java.util.Random` с одинаковым seed, проверь границы массива и повторяемость последовательности. Сначала можно отлаживаться на маленьком фиксированном массиве; финальные замеры делай на распределении задания.

Замерялку собери из шагов 5 и 7:

- заранее создай значения, коллектор, массив результатов, флаг остановки и потоки;
- рабочие ждут общего старта; по желанию добавь `ready`, как в упражнении;
- каждый рабочий вызывает `record(values[index])`, считает вызовы в локальном `long` и циклически двигает индекс;
- после сигнала остановки сохраняет число выполненных вызовов в свой элемент массива;
- главный дожидается всех `join()` и складывает результаты.

Для времени используй `System.nanoTime()`: запомни число до работы и после, затем вычти первое из второго. Разность получится в наносекундах; в одной секунде их миллиард:

```java
double seconds = (t1 - t0) / 1_000_000_000.0;
double opsPerSecond = totalOperations / seconds;
```

Сначала воспроизведи порядок измерения из задания: `t0` перед открытием старта, `t1` сразу после выставления stop, затем `join`. Это приближённый замер: уже начатые вызовы могут закончиться после stop. Сохраняй одинаковую методику для всех вариантов и не считай, что `sleep(5000)` дал ровно 5.000 секунд. Для вычисления скорости нужен фактический интервал.

Правила финального прогона из задания:

1. Прогрев — 5 секунд работы перед замерами, чтобы JVM успела оптимизировать часто выполняемый код; результат скорости отбросить.
2. Пять измерений по 5 секунд, взять медиану — среднее по позиции число после сортировки пяти результатов, то есть третье.
3. Каждый вариант коллектора запускать отдельным процессом `java`. Удобнее запускать отдельно каждую пару «вариант, число потоков».
4. Baseline — исходный вариант для сравнения — без синхронизации запускать только с одним потоком.
5. Использовать `T` из 1, 2, 4, 8, 16, не превышая доступное число логических процессоров.
6. Не печатать, не генерировать случайные числа и не делать общих инкрементов счётчика бенчмарка в горячем цикле — том, который повторяется много раз и скорость которого мы измеряем.

Одна точка занимает около 30 секунд плюс запуск. Для отладки можно временно уменьшить длительность, но такие результаты не переносить в итоговую таблицу. Запускай через **Run**, не Debug.

Каждый отдельный запуск измерения назовём забегом. Если один коллектор используется для прогрева и всех забегов, `count` содержит записи из них всех. Например, 100 записей при прогреве и 200 при измерении дают итог 300, а не 200. Учитывай это при проверке. Либо создавай новый коллектор для каждого забега и считай итог только этого забега. Выбранные правила должны быть одинаковыми для сравниваемых вариантов.

Сначала научись передавать аргументы через `args`: например `args[0]` — вариант, `Integer.parseInt(args[1])` — число потоков. После того как сам реализуешь `Bench`, команды могут выглядеть так:

Имена аргументов — предлагаемый тобой реализуемый интерфейс, готового `Bench` пока нет. В IDEA они задаются в **Run → Edit Configurations → Program arguments**.

## 12. Этап 1: работаем с общими данными по очереди

**Идея:** все пишут в один объект, но меняют его данные по очереди под одним замком. Это знакомое `synchronized` из пункта 4.

Перенеси уже проверенный код для одного потока в класс с общим замком. Например, запись числа 7 должна целиком обновить количество, сумму, минимум, максимум и нужную корзину. Другой поток не должен увидеть половину этих изменений.

На этом этапе один вызов `record` рассматривай как целую операцию над несколькими полями. Лок нужен, чтобы другой защищённый вызов `record` или `snapshot` не увидел середину этой операции. Разные потоки всё ещё существуют, но доступ к этой части общего состояния получают по очереди.

Твои задачи:

1. Защитить **весь набор изменений** одного `record()` одним монитором.
2. Под тем же монитором скопировать все данные для `snapshot()`.
3. Вычислять перцентили по согласованной копии. Для первого варианта проще держать весь `snapshot()` под локом; сокращение секции — отдельное осознанное изменение.
4. Повторить проверки этапа 0.
5. Запустить несколько писателей с заранее известным числом вызовов. После `join()` итог должен точно совпасть.
6. Проверять снимки также во время записи: сумма корзин должна равняться `count`.
7. Отдельно сделать вариант «пустой лок» и измерить его по заданию.

Пустой лок — только эксперимент стоимости блокировки: отсутствие записей в нём намеренное. Не применяй к нему проверку «count равно числу вызовов record» как к полноценному коллектору.

Этот этап станет твоим ориентиром: дальнейшие реализации сравнивай с ним на одинаковой последовательности данных.

## 13. Этап 2: несколько замков вместо одного

**Идея:** у разных групп корзин разные замки. Потоки смогут менять разные группы одновременно.

Разбей корзины на 16 групп. Корзина `b` принадлежит группе `b % 16`. Знак `%` — остаток от деления: корзины 0, 16 и 32 относятся к группе 0; корзины 1, 17 и 33 — к группе 1.

Шард — просто выделенная часть данных. Несколько локов позволяют одновременно менять разные группы корзин. Но теперь нет одного общего момента, когда все группы и сводка прочитаны вместе: защита каждой части отдельно не защищает связь между частями.

Синтаксическая ловушка:

```java
Object[] locks = new Object[16];
```

Это массив из 16 значений `null`, а не 16 объектов лока. Каждый элемент нужно заполнить отдельным `new Object()`. Если заполнить все элементы одной ссылкой, получится прежний общий лок.

Следуй алгоритму задания: сначала увеличь корзину под замком её группы. Затем отдельно обнови `count`, `sum`, `min`, `max` — это общие итоговые числа, поэтому здесь для них нужны `AtomicLong`. Для `min/max` используй CAS-цикл из шага 6. Снимок копирует группы по очереди, а потом поля сводки. Здесь снимок может показать корзины и количество от разных моментов времени. Это ожидаемая проблема, как пара `1, 0` в пункте 9. Сейчас задача — обнаружить её; исправление будет позже.

Напиши отдельный `ConsistencyCheck`. Это стресс-тест: многократно выполняем операции одновременно, чтобы повысить шанс заметить ошибку:


1. Создай новый коллектор, четыре пишущих потока, общий старт, флаг остановки и личные счётчики вызовов.
2. Пока писатели работают, главный поток получает 10 000 снимков.
3. Для каждого вычисляет `bucketTotal = сумма snapshot.buckets()` и сравнивает со `snapshot.count()`.
4. Раздельно считает случаи `<`, `>` и общее число несовпадений.
5. Останавливает рабочих и ждёт их завершения даже при ошибке в проверке. Для этого пригодится `try/finally`: код внутри `finally` выполнится и после обычного окончания блока `try`, и при выходе из него из-за исключения.
6. **После всех join** получает новый итоговый снимок и сравнивает `count` с суммой личных счётчиков вызовов.

В таблице задания запись `sum(buckets)` означает **количество элементов по всем корзинам**. Это не поле `snapshot.sum()`, которое содержит сумму задержек в миллисекундах.

При правильной реализации этапов 2–3 промежуточные снимки могут расходиться, а итог после остановки должен быть точным. Если расходится и итог, ищи потерянные обновления, регистрацию состояния или неверное суммирование.

Отдельно отслеживай исключения в рабочих потоках: `join()` не перебрасывает их в главный поток. Для проверки можно записать ошибку каждого работника в отдельный элемент `Throwable[]` и после `join()` завершить тест ошибкой. Частично отработавший поток не должен выглядеть успешным тестом.

Стресс-тест и бенчмарк — разные программы/режимы. 10 000 снимков в фоне меняют нагрузку: не смешивай их с базовыми замерами пропускной способности задания.

## 14. Этап 3: каждому потоку свои корзины и счётчики

**Идея:** как в пункте 8, выдаём каждому потоку личный объект. Теперь внутри не одно число, а корзины и все итоговые поля. Поток, который добавляет числа, будем называть **писателем**. Поток, который вызывает `snapshot()`, — **читателем**.

Каждый писатель меняет только свой объект. Читатель собирает общий результат: складывает количества, суммы и одинаковые корзины из всех объектов.

Отличия от маленького упражнения:

- состояние содержит 256 корзин и сводку;
- читатель смотрит на состояния, пока владельцы ещё пишут;
- поэтому используй `AtomicLongArray` и `AtomicLong`, как требует задание;
- регистрация состояний и копирование списка ссылок защищаются общим локом.

«Владелец» — просто тот поток, которому выдали объект. Это правило нашей программы, а не встроенный запрет Java: если дать этот же объект другому писателю, он тоже сможет его изменить.

Почему теперь можно увеличивать число через отдельные чтение и запись? Потому что в этот личный счётчик никто другой не пишет. Потерять чужую прибавку невозможно. Но читатель работает одновременно, поэтому простого обычного поля здесь недостаточно: используем методы из задания.

Вот сложную строку из задания разложим на части:

```java
// Писатель, который один меняет это число:
long old = state.count.getPlain();
state.count.setRelease(old + 1);

// Другой поток — читатель:
long observed = state.count.get();
```

`getPlain()` — прочитать своё число без дополнительных правил обмена с другим потоком. `setRelease(...)` — записать новое число так, чтобы читатель при подходящем чтении мог увидеть также изменения, сделанные писателем до этой записи. Здесь подходящее чтение — `get()`: если оно прочитало эту запись, предыдущие изменения писателя тоже будут видны.

Главное сейчас: этот вариант допустим потому, что **писатель у числа один**. Не переноси его на общий счётчик, который увеличивают все потоки. И снимок сразу из нескольких чисел по-прежнему может быть неправильным: пока читаешь одно, писатель уже меняет другое.

У `AtomicLongArray` добавляется индекс: `getPlain(i)`, `setRelease(i, value)`, `get(i)`. У `volatile long[]` volatile относится только к ссылке на массив, а не к его элементам.

**Проверки:**

1. Состояние создаётся один раз на поток для данного коллектора.
2. Два разных коллектора не используют одно состояние из статического `ThreadLocal`.
3. После завершения писателей все итоги точные.
4. Снимки во время записи могут быть несогласованными — объясни это через шаг 9.
5. Если каждый забег создаёт новые потоки, список состояний увеличивается. Не удаляй завершённые состояния, пока их результаты нужны накопительному итогу.

## 15. Этап 4: один набор заполняем, другой читаем

**Идея:** у каждого писателя два набора данных. Сейчас он заполняет набор 0. Когда нужен снимок, просим новые записи отправлять в набор 1, ждём окончания начатых записей в набор 0 и спокойно читаем его.

Такой набор называют **буфером**. Два набора — **двойная буферизация**. Представь два блокнота: один заполняют, из другого переписывают готовые числа. Нельзя начинать переписывать и стирать старый блокнот, пока кто-то ещё дописывает туда строку.

Это самый сложный этап. Пока не понятны пункты 7–9 и предыдущие этапы лабораторной, его можно отложить.

Буфер здесь — обычный набор массивов и полей для временного накопления данных. Идея двух буферов: пока писатель наполняет один, читатель может собирать другой. Однако переключение индекса само по себе не завершает уже начатые записи. Поэтому нужен **протокол** — обязательная для обеих сторон последовательность проверок и действий, которая определяет, когда читать и очищать старый буфер безопасно.

| Переменная | Что означает | Кто меняет |
|---|---|---|
| `active` | В какой буфер сейчас должны входить новые записи | Читатель под локом снимков |
| `inside` каждого писателя | В каком буфере писатель объявил своё присутствие; `-1` — нигде | Только этот писатель |
| Буферы 0 и 1 | Корзины и сводка интервала | Владелец при записи; читатель при безопасном сборе и очистке |
| Накопленная сводка | Всё, что читатель уже собрал | Читатель под локом снимков |

Пройди на бумаге три расписания:

1. Писатель успел войти в старый буфер до переключения. Почему читатель должен дождаться его выхода?
2. Читатель переключил буфер до входа писателя. Как писатель выберет новый?
3. Писатель прочитал старый `active` и остановился **до** объявления `inside`. Читатель переключил индекс и начал сбор. Что предотвращает запись в читаемый буфер?

Ответ на третий вопрос — повторная проверка `active` после объявления `inside`. Только когда понимаешь её необходимость, переноси протокол из задания в код.

Порядок реализации:

1. Класс состояния с двумя обычными буферами и `AtomicInteger inside`, изначально `-1`.
2. Регистрация состояний под **тем же локом**, что защищает `snapshot()`.
3. Вход писателя с повторной проверкой активного индекса.
4. Обновление выбранного буфера и гарантированный выход с очисткой `inside`.
5. Читатель переключает индекс, ждёт вышедших из старого буфера, собирает данные и очищает его.
6. Снимок возвращает копию накопленной сводки.

Для выхода используй идею `try/finally`: даже при исключении нужно снять отметку «пишу». Проверку входного числа лучше делать до установки отметки. При этом `finally` не откатывает изменения: если успели увеличить только часть полей, он сам не исправит их.

На этом этапе важны конкретные методы из задания. Их нельзя свободно заменять друг другом:

| Код | Зачем он здесь |
|---|---|
| `volatile int active` | Передавать писателям, какой набор сейчас выбран |
| `inside.set(b)` | Писатель объявляет: «собираюсь писать в набор b» |
| Повторное чтение `active` | Проверить, не сменился ли набор, пока объявляли намерение |
| `inside.get()` у читателя | Проверить, не остался ли писатель в старом наборе |
| `inside.setRelease(-1)` | Сообщить: «закончил запись» |
| `Thread.onSpinWait()` | Подсказать процессору, что цикл сейчас только ждёт |

Последняя строка сама по себе не делает данные видимыми и не заменяет правильные проверки. В отличие от `await()` из пункта 7, этот цикл продолжает проверять условие, расходуя время процессора.

В задании ты встретишь `seq_cst`: так в C++ называется строгий порядок некоторых обращений к памяти. Сейчас не нужно разбирать C++: используй именно указанные Java-операции. Их точные правила можно позже посмотреть в [документации AtomicInteger](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/atomic/AtomicInteger.html).

Если процессор временно переключился с писателя на другую работу, читатель будет ждать, пока писателю снова дадут выполнить код и закончить запись. Поэтому точное время ожидания заранее не известно. Добавление нового состояния в общий список также всё ещё использует замок.

**Контрольный список:**

- После очистки `count/sum/корзины` равны 0, `min` снова `Long.MAX_VALUE`.
- Глобальная сводка накопительная: два снимка подряд без новых записей возвращают одинаковый итог, не ноль и не двойную сумму.
- Новый поток безопасно регистрируется даже при одновременном `snapshot()`.
- Два читателя не переключают `active` одновременно: они выполняют весь `snapshot()` по очереди под одним замком.
- После `join()` финальный снимок даёт точное число вызовов, сумму и корзины.
- 10 000 снимков во время записи сохраняют `bucketTotal == count`.
- Для дополнительной проверки все писатели могут писать одно значение, например `7`: тогда `sum == 7 * count`, заполнена только корзина 1, непустые `min/max` равны 7.

Не требуй, чтобы снимок показывал буквально всё на одну точную наносекунду: записи, начавшиеся рядом с переключением, могут попасть в этот или следующий снимок. Требуй, чтобы числа внутри снимка подходили друг к другу, а после остановки ни одна запись не потерялась и не посчиталась дважды.

Лишь после успешной версии сделай отдельно эксперимент без повторной проверки `active`. Запиши реальные результаты стресс-теста и отклонение финального счётчика. Ошибка не обязана проявляться в каждом запуске. Можно временно добавить задержку в уязвимое место, чтобы исследовать расписание, но это отдельный диагностический запуск, не замер скорости. Верни корректную проверку перед основными измерениями.

## 17. Если что-то не запускается

| Симптом | Что проверить |
|---|---|
| Нет зелёного запуска возле `main` | JDK проекта, Sources Root и точную сигнатуру `main` |
| `Cannot resolve symbol` для классов JDK | Настроен ли SDK у модуля; правильный ли `import` |
| Пакет не соответствует пути | `practice/src` — корень, под ним `practice/S01Syntax.java` |
| `Could not find or load main class` | После компиляции запускаешь с правильным `-cp` и полным именем пакета |
| `UnsupportedClassVersionError` | Запускающая Java старее байткода; выровняй JDK или пересобери с `--release 17` |
| Нельзя захватить `k` в лямбду | Внутри итерации сделай `final int id = k` |
| `InterruptedException` требует обработки | В `main` можно `throws`, в `Runnable` нужен `try/catch` |
| `IllegalMonitorStateException` | `wait/notifyAll` вызваны без владения монитором этого же объекта |
| Рабочие не заканчиваются | Видимость stop, ожидание на защёлке, забытый сброс `inside`, взаимное ожидание локов |
| Счётчик иногда правильный, иногда нет | Проверь общий `++`, совпадение объектов локов и порядок чтения после `join` |
| Время сильно скачет | Убери Debug и вывод из цикла, проверь прогрев, фоновые процессы, повторные измерения |
| Внезапно понадобилась сеть | Проверь, что запускаешь обычный Java-модуль, а не Gradle-конфигурацию другого проекта |

Чтобы разобраться в зависании, начни с `jps -l`, затем `jstack PID` в терминале того же пользователя и JDK. Замени `PID` на число из списка. Если подключение запрещено системой, можно остановить программу или посмотреть потоки в отладчике IDEA. Для замеров отладчик отключай.
